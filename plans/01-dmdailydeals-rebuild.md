# DMDailyDeals rebuild — product & technical plan

Status: draft for review · Written 2026-11-21 · Branch: `develop` (the old Express/EJS/Vite code is frozen on `legacy-version`)

How to use this file: each phase can be done in a fresh session. Read the Primary goal, Decisions, Architecture and Phase 0 first, then only the phase you're doing.

## Primary goal

Someone who arrives at dmdailydeals.com, whether from Google, an AI assistant, the newsletter or Telegram, sees today's drop: one hero deal plus 5–10 curated picks across home, tech and travel. They know exactly when the next drop lands, can see why each discount is real, and click through to the store via a tracked link. Every page is server-rendered HTML that search engines and AI crawlers can read, index and cite.

## Architecture at a glance

```
                Cloudflare (DNS, TLS, static-asset cache, AI-crawler settings)
                                   │
                         Caddy (TLS to origin)
                                   │
   ┌───────────────────────── VPS · Docker Compose ─────────────────────────┐
   │  web      Next.js 16.4 + Payload 3.94 (one standalone image)           │
   │           ├─ (frontend) public site: ISR pages + tag cache             │
   │           ├─ (payload)  /admin, /api (REST), /api/payload-jobs/run     │
   │           └─ /go/[id]   outbound redirect + click log                  │
   │  cron     curl loops → /api/payload-jobs/run (A: drops+default every   │
   │           minute · B: ai queue, one job at a time, long timeout)       │
   │           (AI draft jobs call the AI provider + search API from web)   │
   │  postgres Postgres 17 (volumes: data) · media volume for uploads       │
   │  umami    self-hosted analytics (Phase 7)                              │
   └────────────────────────────────────────────────────────────────────────┘
```

**Key choices and why:**

1. **Payload runs inside the Next app** (one codebase, one image). Payload provides the admin panel, auth, media, drafts, scheduled publishing and the Jobs Queue.
2. **Cache Components stay OFF for now.** We use ISR plus `unstable_cache` with tags and `revalidateTag(tag, 'max' | { expire: 0 })`. This is the pattern Payload's own `website` template uses. Cache Components has known rough edges with the Payload admin, and under it a request-time `notFound()` returns a 200 status (a "soft 404"). Revisit when Payload v4 is stable.
3. **Jobs run over HTTP, not through the Payload CLI.** A `cron` container calls `GET /api/payload-jobs/run` every minute with `CRON_SECRET`. Three reasons:
   - The standalone image has no tsx and no full `node_modules`, so `payload jobs:run` can't run in it.
   - `revalidatePath`/`revalidateTag` throw outside a Next request context. Payload issues #15388 and #16392 are both still open in 3.x.
   - A job run inside a route handler has that request context.

   ✅ **Verified by the Phase 1 spike (2026-11-21):** a job run through `GET /api/payload-jobs/run` called `revalidateTag('spike', { expire: 0 })` without error, and the tagged static page regenerated on the next request. No fallback endpoint is needed.
4. **Migrations run on startup** via `prodMigrations`, again because the standalone image can't run `payload migrate`.
5. **Cloudflare caches static assets only** at launch. `revalidateTag` doesn't purge a CDN, so caching HTML at the edge would need purge calls. Origin ISR is fast enough to start with.
6. **A single web instance.** ISR and the tag cache live on local disk and in memory. Running several instances would need a Redis cache handler, which is deferred.

## Phase 0 — Documentation discovery (done 2026-11-21)

> **How this serves the primary goal:** every later phase is built on the APIs that actually exist in the versions we'll install, so nothing in the drop engine, the cache or the SEO layer rests on invented or outdated calls.

### §A Payload (3.94.1 stable; v4 is beta)

**Versions and packages**
- `payload@3.94.1` is the npm `latest` (released 2026-11-20). `4.0.0-beta.*` exists; **do not use v4 APIs**.
- Node engines: `^22.23.5 || ^24.22.3 || >=26.13.1`. **Local Node 25.2.1 is outside this range**, so pin Node **24.22.3**.
- Next peer range: `>=16.4.5 <17` (or specific 15.x ranges). The templates pin `next 16.4.6`.
- React peer range: `~19.2.9 || ^19.3.1`.
- Every `@payloadcms/*` package must be on **exactly** the same version as `payload`.

**Scaffold**
- Command: `npx create-payload-app@latest -t website --db postgres --use-pnpm`.
- It writes `DATABASE_URL` (not `DATABASE_URI`) and `PAYLOAD_SECRET`.
- The website template does **not** set `output: 'standalone'`. Add it.

**Postgres adapter**
- `postgresAdapter({ pool: { connectionString: process.env.DATABASE_URL } })`.
- `push` is on in development. Use `migrate:create` once a feature is done.
- `prodMigrations` runs migrations on startup.
- Do not mix push mode and migrations on the same database.

**Collection features we rely on**
- `slugField()` (marked experimental).
- Drafts: `versions: { drafts: { autosave, schedulePublish } }`. **schedulePublish needs a job runner** and queues into the `default` queue.

**Hooks**
- `CollectionAfterChangeHook<T>`: `({ doc, previousDoc, req, operation, context }) => doc`.
- The template's revalidate hooks are the only official pattern: `revalidatePath(path)` plus `revalidateTag(tag, 'max')`, skipped when `context.disableRevalidate` is set.

**Local API**
- `getPayload({ config })`, with `config` imported from `@payload-config`.
- Calls: `payload.find/findByID/create/update/count/findGlobal/updateGlobal`.
- `overrideAccess` defaults to `true` in v3.
- Run scripts with `payload run src/scripts/x.ts`.

**Jobs Queue**
- Task config: `{ slug, handler: async ({ input, job, req }) => ({ output }), inputSchema, outputSchema, retries, schedule: [{ cron, queue }] }`.
- Queue a job: `payload.jobs.queue({ task, input, queue?, waitUntil? })`.
- Run over HTTP: `GET /api/payload-jobs/run?queue=&limit=&allQueues=`. This also handles schedules by default and is protected by `jobs.access.run` (template pattern: `Authorization: Bearer ${CRON_SECRET}`).
- Make tasks **idempotent**: claims are atomic, but execution is not exactly-once.

**Plugins and uploads**
- SEO: `seoPlugin({ generateTitle, generateURL })`, with fields from `@payloadcms/plugin-seo/fields`. Also `redirectsPlugin`.
- Uploads: `upload: { staticDir (absolute), imageSizes, focalPoint }`, plus `buildConfig({ sharp })`.

**Docker**
- Multi-stage Dockerfile: standalone output, user uid 1001, `node server.js`.
- Media must sit on a volume that uid 1001 can write to.
- `NEXT_PUBLIC_*` values are build-time variables.

**Copy from** `payloadcms/payload` tag `v3.94.1`, `templates/website/`:
- Config: `src/payload.config.ts`, `src/plugins/index.ts`
- Collections and access: `src/collections/Media.ts`, `src/collections/Posts/index.ts` (drafts + SEO tab + slug pattern), `src/access/*`
- Revalidate hooks: `src/collections/Pages/hooks/revalidatePage.ts`, `src/hooks/populatePublishedAt.ts`
- Utilities: `src/utilities/{getGlobals,getDocument,generateMeta,mergeOpenGraph,getURL}.ts`
- Infra: `Dockerfile`, `.env.example`

From `templates/with-postgres/`: `src/migrations/index.ts` and the `ci` script.

**Anti-patterns**
- Removed in v3: `payload.init()`, Express `server.ts`, `PAYLOAD_PUBLIC_*`, `upload.staticURL`, default-export plugins.
- Not real: `payload jobs:work`, `jobs:start`, `jobs:schedule`, a `queue` option on `schedulePublish`, an official Payload sitemap plugin, a built-in revalidation helper.
- v4 only: top-level `storage`, `@payloadcms/transformer-sharp`, `jobs.processingLease`.
- **Never call `revalidatePath`/`revalidateTag` from a job running outside a request**: it throws `Invariant: static generation store missing`.
- **Never run `jobs:handle-schedules` alongside `autoRun` on the same queue**: you get duplicate jobs.

### §B Next.js 16.4.6 · React 19.3 · Tailwind 4.3 · shadcn CLI 4

**Next 16 breaking changes**
- Request APIs are async only: `await params`, `await searchParams`, `await headers()`, `await cookies()`.
- `middleware.ts` → `proxy.ts`.
- Turbopack is the default for dev and build, and `next build` **fails if a `webpack` config is present**. Check the Payload template config, and use `next build --webpack` if needed.

**Caching (Cache Components off)**
- `revalidateTag(tag, profile)`: the second argument is required. Use `'max'` for stale-while-revalidate, or `{ expire: 0 }` to expire immediately.
- `revalidatePath(path, type?)`: `type` is required for dynamic patterns.
- Both work only in Route Handlers and Server Functions.
- `unstable_cache(fn, keys, { tags, revalidate })` is still supported and survives deploys.
- Route segment `revalidate` and `dynamic` exports remain valid while Cache Components is off.
- Regeneration happens on the **next request** after invalidation, so warm key URLs after a drop.

**Metadata, sitemaps, OG images**
- `generateMetadata({ params, searchParams }, parent)`; `metadataBase` in the root layout; `alternates.canonical`; `robots.googleBot['max-image-preview']`.
- `app/sitemap.ts` returns `MetadataRoute.Sitemap`. Use `generateSitemaps()` to split; it receives `id: Promise<string>`, so convert with `Number()`.
- `app/robots.ts` returns `MetadataRoute.Robots` with `rules[]` (`userAgent` can be a string or array).
- OG images: `opengraph-image.tsx` with `ImageResponse` from `next/og` (flexbox only, ≤500 KB, ttf/otf/woff fonts).

**Streaming metadata and AI bots**
- GPTBot, ClaudeBot and PerplexityBot are **not** in the default `htmlLimitedBots` list.
- `htmlLimitedBots` *replaces* that list. Copy the default regex and add the AI bots so they get metadata in `<head>`.

**JSON-LD**
- Use a native `<script type="application/ld+json">` with `JSON.stringify(x).replace(/</g,'\\u003c')`.
- Type it with `schema-dts` (`WithContext<Product>`).

**`/go/[id]` route**
- `GET(request, ctx: RouteContext<'/go/[id]'>)` then `NextResponse.redirect(absoluteUrl, 302)`. The URL must be absolute. Allowed statuses: 301/302/303/307/308.
- Log the click in `after()` from `next/server`.
- Set `Cache-Control: no-store` explicitly.

**Self-hosting**
- `output: 'standalone'`, then `node server.js`. Copy `public/` and `.next/static` yourself.
- The official `examples/with-docker` uses Node 24.13. **Bump it to 24.22.3.**
- The `.next` directory must be writable for the ISR cache.
- `sharp` is required in standalone builds.

**Images and fonts**
- `images.remotePatterns` (URL objects or `{protocol, hostname, pathname}`).
- Payload media: `images.localPatterns: [{ pathname: '/api/media/file/**' }]`.
- The `priority` prop is deprecated; use `preload` or `loading="eager"`.
- `next/font/google` with `variable`, then Tailwind `@theme inline { --font-sans: var(--font-x) }`.

**shadcn and Tailwind**
- Init: `npx shadcn@latest init`. Since 2026-07 new projects default to **Base UI**; use `-b radix` to keep Radix.
- `cn` now comes from the `cn` package.
- Leave `tailwind.config` blank in `components.json`. Tailwind v4 is CSS-first: `@import "tailwindcss"` plus `@theme`.

**Countdown**
- Use a client component that reads the time **only inside `useEffect`**.
- Render `<time dateTime={iso}>` with a server-rendered ISO target, and add `suppressHydrationWarning` on the ticking text.

**Anti-patterns**
- Pages Router APIs (`getStaticProps`, `next/head`).
- `experimental.dynamicIO`, `experimental.ppr`, `images.domains`.
- Single-argument `revalidateTag`.
- `updateTag` or `refresh` in Route Handlers (they only work in Server Actions).
- `export const dynamic` while Cache Components is on (we keep it off).

### §C SEO / AI-SEO specs and integrations

**Structured data**

*Product markup*
- Use **product snippets**, not merchant listings. Merchant listings require that "the merchant has to be the seller", so this site is not eligible.
- Product rich results "only support pages that focus on a single product". Product markup therefore goes on `/deal/[slug]` only.
- `Product` requires `name` plus one of `offers`, `review` or `aggregateRating`.
- `Offer` requires `price`. Recommended: `priceCurrency`, `availability`, `priceValidUntil` (ISO 8601). A past `priceValidUntil` can suppress the snippet.
- Use `Offer`, not `AggregateOffer`; AggregateOffer disqualifies the price-drop enhancement.

*"Was" price*
- `StrikethroughPrice` is documented **only** for merchant listings. Show the was-price in the visible HTML only; do not mark it up.

*Other page types*
- Carousel / `ItemList`: no rich result for products outside the EEA, Türkiye and South Africa (beta). `ItemList` on drop and category pages is optional and gives no rich result.
- `BreadcrumbList`: at least two `ListItem`s with `position`, `name`, `item`. Desktop only.
- `Organization`: no required properties. Put it on the home or about page; `logo` at least 112 px.
- `WebSite`: `name` and `url`, on the root home page only (used for the site name).
- `Article`: `headline`, `image`, `datePublished`, `dateModified` (with timezone), `author`. Suits the dated drop pages.

*Dead or forbidden markup (do not add)*
- `FAQPage`: dead since 2026-05-07.
- `HowTo`: dead.
- Sitelinks search box: dead since 2024-11-21.
- `Event` markup for sales (Black Friday, Prime Day): sales are explicitly ineligible.
- `aggregateRating` copied from retailers: "Don't aggregate reviews or ratings from other websites".
- Merchant-only properties: `hasMerchantReturnPolicy`, `shippingDetails`.

*AI features*
- Google: "Structured data isn't required for generative AI search… no special schema.org markup."
- Pages only need to be indexed and eligible for snippets. **Never set `nosnippet` on deal pages.**
- Structured data must match the visible text.

**Spam policies to design around**
- **Thin affiliation:** copied merchant descriptions add no value. Every deal needs an original `editorNote`.
- **Scaled content abuse and doorway abuse:** no auto-generated store × category × event permutations, and no thin hub pages.
- **Back-button hijacking:** never interfere with browser history.

**Links**
- Use `rel="sponsored"` on affiliate links; it is preferred over nofollow, and `rel="sponsored nofollow"` is fine.
- Disallowing `/go/` in robots.txt is common practice, not Google guidance.

**IndexNow**
- Bulk submit: `POST https://api.indexnow.org/indexnow`.
  - Headers: `Content-Type: application/json; charset=utf-8`.
  - Body: `{ host, key, keyLocation, urlList }`, up to 10,000 URLs.
- Key: 8–128 characters (`a-zA-Z0-9-`), served at `https://dmdailydeals.com/<key>.txt` with the key as its content. The key is public by design.
- Responses: 200 or 202 OK; 400, 403, 422 and 429 are errors.
- Participants: Bing, Yandex, Seznam, Naver, Yep, Internet Archive, Amazonbot. **Google does not participate**; it relies on sitemaps and Search Console.
- Submit only new, changed, redirected or removed URLs.

**Sitemaps**
- Limits: 50,000 URLs or 50 MB per file; an index holds up to 50,000 sitemaps.
- `lastmod` is used only if "consistently and verifiably accurate". Google ignores `changefreq` and `priority`.
- The sitemap ping endpoint is dead (404). Use a `Sitemap:` line in robots.txt plus Search Console.

**llms.txt**
- Format: H1 site name (required), then a `>` summary, free text, and H2 link lists (`- [name](url): note`). An `Optional` H2 holds links agents can skip.
- Google Search does not use it (2026-06-15), and no AI vendor has confirmed reading it. It's cheap to add, so add it, but expect nothing.

**Telegram Bot API (10.4)**
- The bot must be a channel admin with `can_post_messages`. `chat_id` is `@channelname`.
- `sendPhoto`: caption up to 1024 characters, `parse_mode: 'HTML'`, `reply_markup` with inline URL buttons.
- `sendMessage`: text up to 4096 characters, plus `link_preview_options`. `disable_web_page_preview` is gone.
- `sendMediaGroup`: 2–10 items, **no `reply_markup`**.
- Rate: about 1 message per second per chat; on a 429, honour `retry_after`.

**Newsletter delivery** (reference for later; for now subscribers are only stored in our DB)

*Listmonk (self-hosted)*
- Image `listmonk/listmonk`, Postgres ≥ 12.
- API auth: `Authorization: token user:token`.
- Public double opt-in: `POST /api/public/subscription { email, name, list_uuids }`.
- Campaigns: `POST /api/campaigns { name, subject, lists, type, content_type, body }`, then `PUT /api/campaigns/{id}/status { status: "running" }`.

*Resend (hosted)*
- `POST https://api.resend.com/broadcasts { segment_id, from, subject, html, send, scheduled_at }`.

### §D AI provider layer (provider-neutral, OpenAI-compatible) — ⚠️ discovery still needed

Decided on 2026-11-21: AI calls go through a **provider-neutral layer that uses OpenAI's request format**. Candidate providers are **DeepSeek or OpenAI**, switchable by config. The Claude-specific research done earlier no longer applies.

**Known constraints to design around (verify in a discovery pass before Phase 8):**
- **Web search is not portable.** Built-in search differs per provider: OpenAI's is a tool in its own API, and DeepSeek's API is not known to offer one. So research uses a **separate search API**, called through standard function calling (D11). That works the same on any provider.
- **Structured output is not uniform.** Some providers support strict JSON schema, others only "JSON mode". The layer always asks for JSON, then **validates with zod** and retries once with the errors quoted back. That works whether or not strict schema is available.
- Context window, output limits, function-calling support and pricing are per-provider config values. Never hard-code them.

**Discovery pass (run before Phase 8, same reporting contract as Phase 0):** confirm the following, with sources, for each candidate provider:
- the base URL and OpenAI-SDK compatibility
- model IDs
- JSON-schema vs JSON-mode support
- function/tool calling
- context and output limits
- pricing
- rate limits

Also confirm the chosen search API's endpoints, result format, terms and pricing.

**Anti-patterns**
- Provider-specific SDK calls outside the provider layer.
- Model IDs or prices hard-coded in task code.
- Trusting model JSON without zod validation.
- Relying on a provider's built-in web search.

## Phase 3 — Drop engine and outbound links

> **How this serves the primary goal:** this phase delivers the daily ritual (a new drop at a fixed time, an accurate countdown) and the tracked click-out that will earn money once programs approve.

**What to implement**
1. `getNextDropAt(now, settings)` utility, pure and unit-tested; it feeds the countdown and default deal expiry.
2. A `publishDueDrops` task scheduled every minute (`schedule: [{ cron: '* * * * *', queue: 'drops' }]`).
   - It runs through the HTTP runner. Cron loop A calls `?queue=drops` then `?queue=default` every minute. The `ai` queue has its own loop (Phase 8), so a slow AI job can never delay a drop.
   - It is idempotent:
   - Find drops where `status = scheduled` and `publishAt <= now`.
   - Set them live and archive the previous drop.
   - Expire deals whose `expiresAt <= now`.
   - Then queue the follow-up tasks below.
3. Follow-up tasks, each retried on its own:
   - `revalidateDrop`: tags `drop:current`, `drops`, the affected categories and stores, and `sitemap`; then warm `/` and `/drops/<date>` with a GET.
   - `pingIndexNow`: see §C.
   - `postDropToTelegram`: §C, Phase 7.
   - `sendDropNewsletter`: **deferred** until newsletter delivery is chosen. Subscribers are only collected for now.
4. `/go/[id]` route handler:
   - Resolve deal → store → `linkTemplate` (`{url}` and `{encodedUrl}` substitution).
   - 302 to the absolute URL with `Cache-Control: no-store` and `X-Robots-Tag: noindex`.
   - **Never** set `Referrer-Policy: no-referrer`: Amazon's anti-cloaking rule (§C) requires the referring site to be identifiable.
   - Log the click via `after()`: `CF-IPCountry`, a bot check on the user agent, and `fromPath` from the referer.
5. ~~`/api/internal/revalidate`~~: not needed (the Phase 1 spike passed).

**Doc references:** §A jobs (task shape, `schedule`, idempotency, HTTP runner); §B `revalidateTag` signature, `NextResponse.redirect`, `after()`.

**Verification checklist**

## Phase 9 — Production deploy on the VPS

> **How this serves the primary goal:** the site has to be live, fast, secure and backed up at dmdailydeals.com, with the drop running unattended every day.

**What to implement**
1. Dockerfile: the official `with-docker` multi-stage build, bumped to `node:24.22.3`, with pnpm, standalone output, a writable `.next`, sharp, and `NEXT_PUBLIC_*` passed as build args.
2. `compose.prod.yml` with these services:
   - `web`
   - `cron`, with the bearer secret:
     - loop A every 60 s: `/api/payload-jobs/run?queue=drops`, then `?queue=default`
     - loop B: `?queue=ai&limit=1&disableScheduling=true` with a long timeout
     - both call `web:3000` directly over the Docker network, bypassing Cloudflare's timeouts
   - `postgres` (volume)
   - `umami`
   - `caddy` (TLS)

   Plus a media volume owned by uid 1001.
3. Cloudflare:
   - Proxied DNS, SSL "Full (strict)".
   - Cache static assets only.
   - **AI crawl controls set to allow search and answer crawlers** (§C).
   - Forward `CF-IPCountry`.
4. Backups: nightly `pg_dump` plus a media tarball to off-VPS storage, with a restore drill documented.
5. Deploy: a GitHub Actions workflow that builds and pushes the image, then on the VPS runs `docker compose pull && up -d`. Migrations run on boot via `prodMigrations`.
6. Search Console and Bing Webmaster Tools verification, plus an uptime monitor on `/` and `/api/health`.

**Doc references:** §A Docker; §B self-hosting; §C Cloudflare.

**Verification checklist**
- `https://dmdailydeals.com` serves the seeded drop over HTTPS.
- A scheduled drop goes live unattended at D2 time.
- A restore from backup works on a scratch database.
- Robots and sitemap are reachable, and the Cloudflare AI settings are checked against §C.

**Anti-pattern guards**
- No secrets baked into the image.
- No `postgres:latest` and no `trust` auth.
- No more than one `web` replica (the cache is local; see the architecture notes).
